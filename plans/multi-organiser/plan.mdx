## Objective

Turn poster-judging from an app you run for one event into a hosted service where
organisers you have never met run their own events, on a public URL, without being able
to see or touch each other's data.

**Done means:** two organisers can each hold an event on the same deployment; neither can
read, mutate, or even confirm the existence of the other's posters, judges, rubric, or
results; every resource is reachable through a RESTful CRUD API with correct verbs and
status codes; new organisers arrive by redeeming an invite rather than by you running SQL;
and the whole thing is deployed on Vercel against Supabase Postgres.

The judge experience does not change at all. Judges keep typing an 8-character code at
`/`, and the code alone still resolves them to their event.

<Callout id="status" tone="success">

**Phases 1, 2 and 3 are implemented** on branch `multi-tenant-phases-1-2` — 211 tests
passing, typecheck, lint and build clean. A second organiser is safe to add, and all 28
REST endpoints are live and documented at `/api/openapi.json`. What remains before
outside organisers can arrive on their own is Phase 5: creating an account still means
running SQL by hand.

Each phase below carries its own status. Three things landed differently from the
original design, all noted in place: `org_invites` shipped early in `0006`, the service
layer turned out **not** to be unit-testable the way this plan assumed, and one endpoint
became `PUT` where the plan said `PATCH`.

</Callout>

<Callout id="risk-today" tone="risk">

**This was a security project before it was a feature project.** The schema was already
multi-*event*, but nothing above it was multi-*organiser*: `admins` was a flat global
allowlist, `events` had no owner, and every admin action checked "are you *an* organiser"
rather than "do you own this one." The moment a second organiser account existed, those
stopped being missing features.

The sharpest edge was `regenerateAllCodes(eventId)` — it returned **every plaintext judge
code** for whatever event id it was handed, and rotated the stored hashes on the way out.
One request would take over another organiser's judging panel and lock their real judges
out mid-event. `tests/tenancy.test.ts` now pins exactly that case, asserting both that
the write is refused and that the victim's `code_hash` is untouched.

Two smaller holes closed with it: the poster-detail page loaded any poster by UUID and
then trusted `poster.event_id`, handing over another event's full per-judge scores and
comments; and `getPrimaryEvent()` returned one global event for every admin, so a second
organiser would have signed in and landed on the first one's dashboard.

</Callout>

## Scope

**In scope.** An org/membership ownership model; a service layer that owns authorization
and validation; ownership enforcement on all 18 admin actions and every admin read; a
RESTful HTTP API over every resource; the event moved into the admin URL; invite-gated
organiser signup; and the deployment and scale work needed to run this for many tenants at
once.

**Not in scope.** The judge *interface*, whose offline behaviour is delicate and stays as
it is. The judge authorization path is already tenant-correct end to end — the session JWT
carries `{judgeId, eventId}`, `signIn` reads `event_id` from the judges row and never from
the client, and `save_submission` re-derives the event in SQL and refuses cross-event
posters and criteria. Also out: API tokens for external clients (D11 defers them),
per-org branding, billing, org deletion and data export, and Supabase Realtime, which is
structurally blocked by the RLS deny-all model and for which polling is the intended
answer.

<Callout id="rls-note" tone="warning">

**RLS is not a safety net here.** Every table is RLS-enabled with no policies, but the app
connects over `DATABASE_URL` as the role that owns the tables, and an owner bypasses RLS.
That deny-all exists to make a leaked anon key worthless — it does nothing for tenant
isolation. Every tenancy check must live in application code or in the SQL predicate
itself, which is why the enforcement pattern below folds ownership into the mutating
statement rather than trusting a policy.

</Callout>

<Callout id="d1-rationale" tone="decision">

**D1 is the pivotal one.** `tests/schema.test.ts` runs migrations against in-memory PGlite,
which has no Supabase `auth` schema — that is why `0004_supabase_auth.sql` is excluded
today. Keeping `memberships` portable with a bare `admin_id`, combined with D2 making
membership the grant, means **every tenancy predicate the app runs is executable under the
existing test harness**. That is the only reason the cross-tenant denial tests in Phase 4
are possible at all. If `memberships` went into the Supabase-only lane, the tenancy
boundary would be the one part of the system that could never be tested.

</Callout>

`alter column org_id set not null` is safe on an empty database: the update touches
nothing and the constraint holds vacuously. `0007_org_membership.sql` then adds the FK
from `memberships.admin_id` to `admins`, and backfills every existing admin as an `owner`
of the bootstrap org — so your own account keeps working untouched across the whole
migration.

**Shipped differently:** `org_invites` landed here in `0006` rather than waiting for its
own migration in Phase 5. Creating the table costs nothing until something writes to it,
and putting it in the portable lane makes the redemption queries testable under PGlite
for free — the same reasoning that put `memberships` there. Phase 5 therefore adds no
migration at all, only the actions and the UI.

`scripts/seed.ts` and the `tests/schema.test.ts` fixture both insert events directly and
will fail on the new `not null` until they pass an `org_id`.

## Phase 2 — Service layer and authorization · **shipped**

<Callout id="smallest-cut" tone="decision">

**This is the smallest cut that makes a second organiser safe, and it does not need the
routing change or the API.** After Phase 1 every admin belongs to exactly one org, so
`getPrimaryEvent()` only has to become `getPrimaryEventForAdmin(adminId)`. Each admin
still sees one event — now provably theirs — with every write ownership-checked. Zero URL
changes, zero component prop changes. Ship this before organiser #2 exists; everything
after it is product work rather than security work.

</Callout>

<Callout id="service-timing" tone="decision">

**The service extraction belongs in this phase, not after the API is designed.** Phase 2
already rewrites the authorization inside all 18 actions. If the services are extracted
later, every one of those actions gets opened twice — and the second pass is the one where
a check quietly goes missing. Extract `lib/services/*.ts` here, make the actions thin
wrappers over it, and Phase 3's Route Handlers become a transport adapter with no
authorization logic of its own.

</Callout>

### The shape of a service

A service function takes an **explicit actor** and never touches cookies, `redirect()`, or
`revalidatePath()` — those belong to the transport. It returns a discriminated result so
each adapter can translate failure its own way: a Server Action into `{ error }` for the
existing UI convention, a Route Handler into a status code.

<Code

  filename="lib/services/posters.ts"
  language="ts"

<Callout id="csrf" tone="risk">

**Server Actions get CSRF protection from Next; Route Handlers do not.** Next validates
the `Origin` header against the host for Server Action invocations. A cookie-authenticated
`POST /api/…` has no such protection, so any site the organiser visits could issue writes
against their session. Every mutating handler must pass through one
`requireSameOrigin(request)` helper that requires `Sec-Fetch-Site: same-origin` (falling
back to an `Origin`-vs-host comparison for older browsers) and returns **403** otherwise.

This is also why D11's ordering is clean: `Sec-Fetch-Site` is browser-only, so it is
exactly the right check while the API is browser-only. When Bearer tokens arrive, a
token-authenticated request skips the origin check entirely — tokens are not ambiently
attached to requests, so there is no CSRF surface to defend.

</Callout>

### Conventions

<Table
  id="api-conventions"
  columns={["Concern", "Rule"]}
  rows={[
    ["Cross-tenant access", "**404, never 403.** A 403 confirms the resource exists. `not_found` covers both 'no such thing' and 'not yours' — the caller cannot distinguish them."],
    ["Verbs", "`GET` read · `POST` create into a collection · `PATCH` partial update · `PUT` replace an addressable resource or whole collection · `DELETE` remove. No verbs in paths."],
    ["Status codes", "`201` + `Location` on create · `204` on delete · `409` conflict (judging closed, duplicate slug, spent invite) · `422` validation · `429` throttled · `401` no session · `403` origin check failed"],
    ["Error body", "`{ \"error\": { \"code\": \"not_found\", \"message\": \"…\" } }` — `code` is the `ServiceError` union, so clients branch on a stable string rather than prose."],
    ["Collections", "`{ \"data\": [...], \"next\": null }`. The envelope exists so cursor pagination can be added without a breaking change."],
    ["Secrets in responses", "Any body carrying a plaintext judge or invite code is sent `Cache-Control: no-store` and is excluded from request logging."],
    ["Validation", "One Zod schema per request body, at the handler boundary. The three dependency-free modules (`scoring`, `assign`, `codes`) stay dependency-free — this is a new dependency at the edge only."],
    ["Versioning", "Unversioned while browser-only. The first external consumer is what earns `/api/v1`; adding it later is a directory move plus a rewrite rule."],
    ["Proxy", "`proxy.ts` does **not** match `/api/*`, and should not. Handlers resolve their own actor, exactly as Server Actions do."]
  ]}

An OpenAPI 3 document lives at `openapi.json`, is served from `/api/openapi.json`, and is
covered by a test asserting every `app/api/**/route.ts` exported method has a matching
spec entry — and, in the other direction, that the spec documents nothing unimplemented.
The same test fails a mutating handler that omits `requireSameOrigin`, or any handler
that reaches the database instead of a service. Both directions were confirmed to go red
against deliberate regressions before being kept.

**Shipped differently:** replacing a criterion became `PUT
/api/events/{eventId}/criteria/{criterionId}` rather than `PATCH`. The existing service
takes a whole criterion, and the rubric UI always sends every field, so the request
replaces the resource rather than merging into it — which is what `PUT` means. `PATCH`
would have advertised partial updates the service cannot perform.

**Also worth knowing:** the same-origin guard runs *before* the session check, so a
cross-site probe gets 403 without learning whether a session exists. Verified against a
running server alongside the 401 and 404 paths.

## Phase 5 — Invite-gated signup · not started

A new organisation can only come into existence by redeeming a code you minted from a
shell. There is no UI that creates one, which is the whole answer to "signup is not open."

/>

`auth.getUser()` is server-revalidated, so `email_confirmed_at` cannot be forged by a
client — that check is the belt, and Supabase Auth's "Confirm email" setting is the
braces. `select … for update` plus the in-transaction `used_at is null` check makes
redemption single-use under concurrent clicks. The `admins` insert must share the
transaction with the membership, or a partial failure leaves a signed-in organiser with no
org — which is already the README's most common setup snag and an infinite
`/admin` ↔ `/admin/login` bounce.

Invite codes are two `generateCode()` calls joined into 16 characters (D7). Because
`normalizeCode` hard-requires exactly 8, an invite code can never be mistaken for a judge
code by the sign-in page. They get a **separate `INVITE_CODE_PEPPER`**, so rotating
`JUDGE_CODE_PEPPER` — documented as invalidating every judge code — does not also silently
void every outstanding invite. Redemption throttling reuses `isRateLimited` verbatim;
`login_attempts.code_hash` is plain text with no FK, so it buckets invite hashes with no
schema change.

`scripts/bootstrap-admin.ts` replaces README step 4's raw SQL, which now creates an admin
with no org. First-signup-wins is explicitly rejected (D8): it is a race on a public URL
and a permanent footgun if the table is ever truncated.

<Callout id="signup-tradeoff" tone="info">

**Stated tradeoff.** Anyone with the anon key can still call `supabase.auth.signUp` and
create an `auth.users` row. That grants **nothing** — the membership row is the grant.
Closing it would mean either a service-role key in the Vercel environment or an edge
captcha, neither of which is worth it. The required email match on invites means a junk
account still cannot redeem someone else's code.

</Callout>

## Phase 6 — Tests · **shipped alongside Phase 2**

D1 and D2 make the existing PGlite harness sufficient: `memberships` is portable and
membership is the grant, so every tenancy predicate is executable under it.

`tests/schema.test.ts` gains `0006_organisations` and an org in its fixture. Leave its
assertions alone — them passing unchanged is the proof that adding `org_id` disturbed
none of the scoring math or `save_submission`.

`tests/tenancy.test.ts` is new: two orgs, two admin uuids, an event each. For each string
in `lib/sql/scoped.ts`, run it with the **wrong** admin id and assert zero rows *and that
the target row is unchanged*; then with the right id and assert one row. Six mutations,
two directions each. Plus slug uniqueness per org, the invite single-use / expiry /
email-mismatch branches, and a re-assertion that `save_submission` still refuses a
cross-event poster with two orgs in play.

`tests/actions-scoped.test.ts` is a lint rule in test's clothing: read
`app/actions/admin.ts` as text, extract every exported async function, and assert each
body calls into `lib/services/`. Extend the same trick to `app/api/**/route.ts` — every
exported `GET`/`POST`/`PATCH`/`PUT`/`DELETE` must reach a service function, and every
mutating one must also call `requireSameOrigin`. It is the only thing that stops someone
adding a nineteenth unscoped action, or a route handler that queries the database
directly, six months from now — which is exactly how the codebase reached its current
state.

**Corrected during implementation.** This plan assumed the service functions would be
directly unit-testable by passing a fabricated actor. They are not: they import
`@/lib/db`, which imports `server-only`, which throws outside a react-server context —
the same constraint that already forces `scripts/seed.ts` to import `lib/db/client`
instead. Adding an injectable query seam purely for tests was not worth it, because the
SQL strings are where the ownership decision actually lives.

So the coverage sits one layer lower and is stronger for it: `tests/tenancy.test.ts`
executes the exact statements from `lib/sql/scoped.ts` against PGlite. Every denial case
asserts both that zero rows came back **and** that the target row is unchanged — a row
count alone would still pass if the write had gone through and simply returned nothing.

`0007` is covered too, despite living in the Supabase-only lane: shimming a bare `admins`
table into PGlite is enough to run it verbatim and prove both backfill paths and the
foreign key. That upgrade would otherwise first execute on a live database.

## Phase 7 — Scale and deploy · not started

<Callout id="view-pushdown" tone="risk">

**The highest-value item here, and a two-word fix per view.** `0002_views.sql` groups by
`s.id`, `p.id` and `j.id`. `event_id` is selected via functional dependency on the primary
key but is **not in the group-by clause**, so Postgres cannot push `where event_id = $1`
down below the aggregation. With one event that is free. With 200 tenants, **every
dashboard poll re-aggregates every submission on the platform.** Add the event column to
each `group by` — semantically a no-op, since both are functionally dependent on the PK,
but it puts `event_id` in the planner's group clause. Change no arithmetic:
`tests/schema.test.ts` will catch you, and `lib/scoring.ts` must keep mirroring the file.

</Callout>

**Connection pooling.** `lib/db/client.ts` sets `max: 5` per lambda instance, and each
Vercel instance gets its own module scope — so N warm instances means 5N connections.
Against the transaction pooler (6543) those are cheap Supavisor client slots multiplexed
onto a small server-side pool; against the direct connection (5432, ~60 on Free) it would
fall over at twelve instances. The existing "use 6543" decision is what makes this
survivable, so nobody should "simplify" it. Drop `max` to **3** and `idleTimeoutMillis`
to **5s**; leave `connectionTimeoutMillis` and the `pool.on("error")` handler alone, since
both are load-bearing.

**The 15-second poll.** `components/auto-refresh.tsx` re-renders the whole RSC tree every
15s — roughly four queries per tick per open dashboard. It already pauses on hidden tabs.
Add an adaptive interval (15s while `status === 'active'`, 60s otherwise; most open
dashboards at any moment are draft or locked, so this alone cuts steady-state load about
fourfold) and an idle stop after ~10 minutes without interaction, since a dashboard left
on a projector overnight currently polls 5,760 times.

**Deployment.** Pin the Vercel function region to the Supabase project region — each admin
render is 3–8 sequential round trips, so this is the single biggest latency win. Add
`maxDuration = 30` to the CSV export route. Two new env vars (`INVITE_CODE_PEPPER`,
`NEXT_PUBLIC_SITE_URL`) take the count from five to seven; `NEXT_PUBLIC_*` are inlined at
build, so changing Supabase projects is a rebuild rather than an env edit. Set
`statement_timeout` for the app role as an **ops step, not a migration** — `npm run
migrate` runs DDL on the same role and must not inherit it. Add CI running `npm test`,
`npm run lint` and `npm run build`; none exists today.

<Callout id="cookie-secure" tone="warning">

**`lib/auth/judge-session.ts` sets the judge cookie `secure: false`**, with a documented
rationale about plain HTTP on a venue LAN. For a hosted HTTPS service that rationale no
longer holds. Make it `secure: process.env.JUDGE_COOKIE_SECURE === "true"`, defaulting
false so existing LAN deployments are unaffected, and set it true on Vercel. Do not simply
flip the literal — that is precisely the regression the existing comment warns about.

</Callout>

## Also worth pulling forward

`importPosters` splits CSV rows on a bare comma while `lib/csv.ts` writes properly quoted

containing a comma. KNOWN-ISSUES.md tracks it as a nuisance — but every new organiser's

**Where this leaves things.** A second organiser is safe to add today, by hand, and can
drive everything over REST. Two gaps stand between that and outside organisers arriving
on their own: creating an account still means running SQL (Phase 5), and each organiser
is limited to a single event because the *UI* has nowhere to put a second one — the API
already handles many events per org, so Phase 4 is now UI-only work.

Ship **Phase 1 + 2 with the Phase 6 tests** as one unit. After that, adding organiser #2
by hand via the bootstrap script is safe, and everything else is additive. The view
pushdown in Phase 7 is a portable migration with zero app changes, so land it early even
though it is listed late — it is not deferrable past roughly twenty events.

**Do not build signup before ownership and enforcement land.** Building the door first
ships a security incident rather than a feature.

**Do not build the API before the service layer.** Route Handlers written against the
current actions would be a second authorization path, and a second place for a check to go
missing — which is the exact failure this whole plan exists to fix.
